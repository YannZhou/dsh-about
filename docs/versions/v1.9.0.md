## 变更说明

本版改的是「更新失败之后」：DSH 本体更新先在隔离目录真实试装并试启动一次，通过后才动正式安装；失败时不再只给一段 npm 输出，而是分阶段记录诊断、定位实际依赖版本，并把历次失败留在磁盘上供随时查看。

### 一、更新前隔离预检

- 从「关于」发起 DSH 更新时，先在任务目录下的临时目录里，用目标版本的真实 npm 包做一次隔离安装。隔离环境拥有独立的 `prefix`、npm cache、`HOME` 与 `DSH_HOME`，不读写正式安装和用户 profile。
- 隔离安装完成后运行目标版本的 `dsh --version`，再以 `127.0.0.1`、随机端口、`--no-open` 启动一次 `dsh web`，并按真实行为完成「带 token 首次请求 → 303 跳转 → 带 cookie 再请求 → 200」的本地登录检查。全部通过后才创建快照并执行正式安装。
- 预检前先读取目标版本在 npm 上声明的 `engines.node`，当前宿主 Node 不满足时直接拦截，不下载、不创建快照。
- 预检失败时正式安装保持原版本，页面显示失败发生在预检的哪一步；正式安装原本的快照、CLI 校验、脚本白名单重试与自动回滚保持不变。
- 预检同样使用独立进程/进程组，超时后先确认进程已停止；无法确认时保留隔离目录且不做清理，但不会把正式安装标记为「需要恢复」。预检中断后可以直接重新发起更新。

### 二、失败诊断

- 记录每次更新各阶段的结果与退出码：`隔离安装`、`隔离校验 DSH 命令`、`隔离检查 Web 启动`、`正式 npm 安装`、`正式 CLI 校验`。
- 目标版本因缺少模块导出而启动失败时，解析实际安装到的依赖包与版本（例如 `fixture-loader@1.1.0`），而不是只显示一段 JavaScript 堆栈。
- 诊断输出统一脱敏：用户主目录折叠为 `~`；URL 中的凭据、`Bearer`、npm/GitHub token、`_auth` 以及环境变量中命中 token / password / secret / api-key 的值替换为 `[已隐藏]`。
- 「上次更新失败」卡片展示失败阶段、错误摘要、逐阶段通过/失败、修复建议和完整诊断；「复制诊断」生成一段可直接交给 AI 复现的修复请求文本。

### 三、报错历史

- 失败记录写入 `$DSH_HOME/dsh-about/jobs/<任务 ID>/failure.json` 与 `$DSH_HOME/dsh-about/last-update-failure.json`，成功更新后**不删除**，便于事后排查。
- 新增 `GET /dsh-about/failure-history`，按时间倒序返回最近 20 条历史；`GET /dsh-about/update-status` 增加 `lastFailure` 字段。
- 页面常驻列表只展示仍需处理的失败。目标版本小于等于当前已安装版本（或同类更新之后已经成功）时，记录标记为「已覆盖」，不再占据页面版面，只保留在「检查更新」右侧感叹号的悬停预览与二级菜单中并灰显。
- 感叹号入口始终保留：有记录时保持琥珀色，无记录时为中性色；点击打开可上下滚动的历史弹窗，支持 `Esc` 关闭、焦点在弹窗内循环，键盘用户不必依赖悬停。

### 四、界面与文案

- 面板间距收紧（10px），「作者」行与「更新源」分隔线对齐，更新与版本记录区块减少空白。
- 更新弹窗的进度文案改为中文阶段名；隔离预检期间显示「正在隔离预检 vX」，预检发现插件 peer 依赖提示时单独标注。
- 去掉安装失败时的手动 `npm install -g --allow-scripts=...` 命令提示。该命令在 npm 12+ 上容易再次踩坑，改为展示结构化诊断与可复制的修复请求。
- 平台支持提示的措辞改为「计划在后续版本停止支持 Windows 和 macOS」，不再承诺具体「下一个版本」；本版仍保留 Windows / macOS / Linux 三平台代码与 CI。此前 `v1.8.3`、`v1.8.4` 已在该提示之后发布，原文案的「下一个版本」已与实际发布不符。

## 验证

- Linux / Node `24.22.3`：仓库全量回归 208 项通过，0 失败、0 跳过（连续运行两次结果一致）。
- `npm run check`、`git diff --check`、`npm pack --dry-run`（58 个文件）通过；新增的 `lib/update-preflight.mjs` 与 `lib/update-diagnostics.mjs` 均在发布包内，更新任务的独立运行时会连同 `lib/*.mjs` 一起复制。
- 用本机已安装的 DSH 在隔离 `DSH_HOME` 实测 `--profile web --host 127.0.0.1 --port 0 --no-open`：输出 `dsh web: http://127.0.0.1:<端口>/?token=…`；首次请求返回 `303` 与 `set-cookie`，带 cookie 再次请求返回 `200`。预检的启动判定与登录跳转判定与该实际行为一致。
- 脱敏函数实测覆盖 `_authToken`、`Bearer`、URL 内嵌凭据、`KEY=value` 与用户主目录。

真实 npm 全局升级、systemd transient unit、Windows/macOS 的进程树与 `bin.dsh` 启动脚本仍需对应环境验证；跨平台结论以发布提交的 GitHub Actions 结果为准。

## 已知限制

- 预检会额外下载并安装一次目标版本，网络较慢时更新总耗时明显增加。预检安装超时会在诊断中显示为「隔离安装超时」，可按修复建议切换更快的更新源或代理后重试；此时正式安装未被改动。
- 预检在临时数据目录中用全新 profile 启动 Web，只证明「目标版本能启动并完成本地登录跳转」，不等于验证用户自己 profile 里的全部插件、数据迁移和真实前端交互。Web 预检依赖目标版本输出的 `dsh web: <URL>` 启动行；若未来版本改动该行格式，预检会以「Web 启动超时」失败并保留正式安装，需要随版本适配解析规则。
- 报错历史接口最多返回最近 20 条。更早的记录仍保留在磁盘，但不在接口返回范围内。
- 失败记录按版本判断是否「已覆盖」，只比较版本号；手工降级或同一版本重装的极端场景下，展示判断可能与直觉略有差异。记录本身不会删除。

## 平台与发布约定

- 本版保留 Windows/macOS 相关代码与 CI；停止支持的具体版本尚未确定，提示文案已改为「后续版本」。
- 本插件继续不声明 `@deepseek-ai/*` peer 依赖，避免更新管理插件因为宿主版本变化而无法加载。
- GitHub Release 标题为 `v1.9.0`，正文只写一行版本文档链接，详细内容均保留在本文件。
- 推送 `v1.9.0` 标签会自动触发 npm 发布与 GitHub Release 创建；发布结果以工作流和 registry 回读为准。
