## 变更说明

问题根因：npm 12 默认拦截依赖的安装脚本。dsh 带原生模块（fs-ext、koffi、node-pty 等），被拦截会缺编译产物，装完 dsh 打不开（典型报错 `Cannot find module '.../build/Release/fs_ext.node'`）。此前一键更新用的是裸 `npm install -g` 命令，在 npm 12 下更新即踩坑。

本次改动分三层：

一键更新（主防线，对未来新增原生依赖免疫）：
- 更新前探测 npm 大版本，≥ 12 自动附加 `--dangerously-allow-all-scripts`，不依赖任何包名清单
- 安装后自动校验（install-scripts 警告 + dsh --version 双信号），不健康时带 `--force` 自动重装一次自愈，仍失败才报错
- 自愈结果通过 selfHealed 字段回传界面，成功对话框会提示"已自动修复"

手动升级兜底（.npmrc 白名单自动维护）：
- 插件每次启动扫描 dsh 实际安装树，把带安装脚本的原生依赖以 name-only 白名单追加进用户 ~/.npmrc（判据与 npm 12 内部一致，注册表 API 够不到深层传递依赖，扫实际树才能拿全）
- 只追加缺失行、绝不改动用户已有配置，写前当日自动备份；npm 老版本无此概念，追加行被忽略无害
- 动态来源：dsh 未来新增任何原生依赖都会被自动纳入，无需插件发版追更

性能与正确性：
- npm registry 数据 60 秒进程内缓存（并发合并、失败自动失效、切源即清），打开设置页/检查更新不再每次直连 npm
- npm config 解析进程内缓存，GET /source 不再每次派生 npm 子进程
- /update 校验顺序调整：同版本/更旧版本的纯本地判断移到网络请求前，不再白等 registry
- 安装失败提示的手动命令补上放行参数（此前是裸命令，npm 12 用户复制执行会再次踩坑）

Windows / macOS / Linux 均按同一逻辑处理（npm 12 的拦截与放行参数跨平台一致；Windows 侧 npm.cmd 解析路径原有实现，本轮复核无缺口）。
