## 变更说明

这一版的主体是**「更新这件事本身要可信」**：修掉三个会让用户看到错误结论的缺陷（旧进程冒充新进程、按钮点了没反应、白屏后永不恢复），并把 npm 12 的脚本放行从过渡开关迁到官方机制。

### 一、重启完成判定加「进程身份」（重要，修的是错误结论）

**缺陷**：`/dsh-about/describe` 的 `version` 读的是**磁盘上的** `package.json`。npm 安装一落盘，**仍在运行的旧进程**就会把版本号报成新版本；而客户端原先只比较 `version` 是否相等，于是「已装好新版但还没退出的旧进程」就能满足「重启完成」，客户端随即刷新页面。

实测该状态真实存在：`旧 pid + 新 version` 的组合持续约 **10 秒**（300ms 一次采样，连续 31 个采样点）。

**修法**：进程启动时生成一个随机 nonce（`randomBytes(8)`），连同 `pid`、`startedAt` 一起下发：

- `GET /dsh-about/describe`、`GET /dsh-about/plugin` 响应新增 `nonce` / `pid` / `startedAt`；
- `POST /dsh-about/update`、`POST /dsh-about/plugin-update` 响应新增 `hostNonce`（应答本次请求的那个、即将退出的进程）；
- 客户端判定改为 **「版本匹配 且 nonce 已变」**。宿主未下发 nonce 时回退为旧的「只比版本号」，保证向前兼容。

nonce 与版本号完全解耦，因此不再依赖「宿主是否已退出」这种时序假设。原先必然会误判的三条路径（看护派生失败导致宿主永不退出、宿主退出慢于客户端首轮轮询、systemd 单元与当前实例不一致）都被堵住。

接口方法备注：`/check`、`/update`、`/ping`、`/plugin-update`、源切换是 **POST**；`/describe`、`/plugin`、`/versions`、`/releases` 是 **GET**。

### 二、升级期白屏自救（修的是「永不恢复」）

**缺陷**：`npm install -g` 会把前端与各客户端插件的 bundle **就地替换**。仍在运行的旧宿主按旧的 rev 哈希去取新文件，得到 `404`，某个客户端插件加载失败并抛出 `SlotAssemblyError`，React 树整体卸载，页面变成空白。而插件原有的「等重启完成 → 刷新」轮询挂在组件副作用里，**随组件一起被卸载**，于是再也没有人去刷新页面 —— 页面空白且**永不自行恢复**（实测 150 秒采样全部为空）。

这**不是**上一条的后果，而是另一条独立路径：页面变白发生在点击后约 11.8 秒，早于重启窗口。

**修法**：新增一个**挂在模块作用域**（而非 React 副作用里）的「安装期白屏自救守卫」：

1. 发起安装 / 插件自更新时布防；
2. 监听 `window` 的 `error` / `unhandledrejection`；
3. 另有 1 秒间隔的兜底探测：连续两次发现 `document.body.innerText` 为空即判定已崩；
4. 判定崩溃后**轮询 `/dsh-about/describe` 直到服务端能应答**，再刷新页面（直接刷新会撞上浏览器的「无法连接」错误页）；
5. 15 分钟后自动收摊，避免"其实没崩"时长期挂定时器。

守卫**不阻止崩溃，但阻止「永久白屏」**：修复前后用同一套 CDP 复现脚本对比，修复后守卫在 +36.7s 触发导航，+39.7s 页面已恢复为可用状态，**不需要用户手动按 F5**。

### 三、版本弹窗默认选中一项

「安装所选版本」按钮的启用条件是「已选中某版本」，而弹窗此前不预选，于是**一打开按钮就是灰的，点了毫无反应**。

现在弹窗打开后自动预选：`latest` 标签 → 最高的 `rc` → 任何已发布到 npm 的版本 → 列表首个；实测默认选中的是稳定的 `rc` 而**不是**更新的 `alpha`。

### 四、更新源不可达时给出可执行的换源建议

验证机上 `registry.npmjs.org` 对 Node 的 `fetch` 不可达，用户此前只看到一句 `检查更新失败：fetch failed`。

现在失败路径会探测「不是当前源」的其它内置源，把第一个可达的写成一句建议，随响应字段 `sourceHint` 下发，面板独立一行显示（不与检查结果行重复）：

```json
{"ok":false,"error":"检查更新失败：fetch failed","sourceHint":"当前更新源（国外官方）不可达，但已检测到「国内镜像」可用（112ms）；可在上方「更新源」处切换后重试。"}
```

### 五、npm ≥ 12 的脚本放行改用**官方机制**（重要，修的是「将来会整体失败」）

npm ≥ 12 默认**拦截**依赖的 install 脚本（RFC [npm/rfcs#868](https://github.com/npm/rfcs/pull/868)）。dsh 带有原生模块（fs-ext / koffi / node-pty / protobufjs / @google/genai / @deepseek-ai/dsh-subprocess-local），被拦截会缺编译产物，装完 dsh 报 `Cannot find module '.../build/Release/fs_ext.node'` 打不开。

此前用的是过渡开关 `--dangerously-allow-all-scripts`。npm 已公告将在下个大版本移除它，而**给 npm 传它不认识的旗标不是忽略、是直接报错退出**（`EUNKNOWNCONFIG`）——也就是说照旧无条件传，npm 13 上「一键更新」会整体失败。

现在改为官方机制：

- 安装参数用 `--allow-scripts=<包名清单>`；
- 清单取三个来源的并集：**实际依赖树扫描** ∪ **历史原生依赖静态表**（兜住目标版本新增的依赖）∪ **用户 `.npmrc` 里已有的条目**（npm 的层优先级是「第一个有配置的层独占」，命令行一旦传了该参数就会整层忽略 `.npmrc`，不并入会把用户批准过的条目丢掉）；
- 包名做严格字符校验后才拼进命令行（Windows 下 npm 走 `shell:true`）；
- 自愈重试的**力度按失败原因升级**：只有首装输出里出现 `install-scripts` 拦截迹象，且 `npm config get dangerously-allow-all-scripts` 显示该逃生开关仍然存在时，才降级用它兜一次；开关已被移除就退回同一份官方白名单，绝不传未知旗标。

实测（npm 12.1.0）：用本插件产出的清单执行 `npm install -g --dry-run`，npm **不再输出任何 install-scripts 拦截警告**（0 个脚本被拦）。

> 顺带一提：因为本插件会同时用「命令行白名单」和「`.npmrc` 白名单」两层，npm 每次安装会打印一条
> `install-scripts .npmrc allow-scripts setting is being ignored because --allow-scripts was passed on the
> command line` 提示（命令行层优先，属正常现象）。它带 `install-scripts` 字样但**不代表有脚本被拦**，
> 因此健康校验已改为只认「N packages had install scripts blocked」这类实锤，
> 不会再把它误判成失败而触发一次无谓的 `--force` 自愈重装。

### 六、`~/.npmrc` 白名单：只在 npm ≥ 12 维护 + 逃生开关

写 `allow-scripts` 白名单这件事有两处问题：在 npm < 12 上写会换来 `Unknown user config "allow-scripts"` 警告（并非原先以为的「被忽略、无害」），且不分版本地在插件启动时就写用户全局配置。

现在：npm 主版本探测失败或 < 12 直接不写；写入延后 3 秒（内部要探测 npm 版本，放启动路径会拖慢引导）；新增 `DSH_ABOUT_NPMRC=off` 完全禁用写入。

**策略定夺（交接项 L3）**：白名单**继续写用户级 `~/.npmrc`，不迁到 profile 级**。理由：npm 自己的官方建议就是 `npm config set allow-scripts=... --location=user`，且用户级是唯一对 `npm install -g` 生效的层；profile 级 `.npmrc` 只在 dsh 自己的安装流程里被读到，迁过去会把手动升级这条兜底路径打断。

**卸载时的处理**：默认**保留**这些条目，并打印说明。删掉它们会让用户下次手动 `npm install -g @deepseek-ai/dsh` 因脚本被拦而装出坏掉的 dsh —— 它们保护的是 dsh 本体，不是本插件。确实要一并清干净（例如 dsh 也卸载了）时显式开启：

```sh
DSH_ABOUT_NPMRC_CLEANUP=1 dsh plugin --profile web remove @yannzhou/dsh-about
```

清理只动「本插件已知的 dsh 原生依赖包名」，用户自己的其它条目与 registry 凭据一律原样保留，改写前自动备份，且幂等。

### 七、自动重启布防失败时立刻提示手动重启（交接项 L6）

启动自动重启的看护进程派生失败时（极罕见，例如 `systemd-run` / node 路径失效），宿主会取消退出但客户端仍在轮询等 nonce 变化，用户要对着「正在自动重启…」**空等约 2 分钟**才看到超时提示。

现在宿主把 `restartArmed` 与 `lastRestartError` 随 `/dsh-about/describe`、`/dsh-about/plugin` 下发；客户端一旦发现「宿主持未布防 且 有失败原因」，立刻转入「需要手动重启」状态并把原因显示出来。

> 注：systemd 单元与当前实例不一致时，宿主确实不会自行退出，客户端仍会轮询到超时（约 2 分钟）——这是保守但正确的行为，此版未改。

### 八、工程与文档

- **打包/归档改用 `git archive`**（交接项 L4）：zip 压目录会丢掉 POSIX 可执行位，`bin/dsh-watchdog` 从 `100755` 掉到 `100644`；后果不是报错而是**静默降级**——看护候选表把 `X_OK` 当必要条件，Linux 上会悄悄跳过 bash 看护。做法写进了 [RELEASE.md](../../RELEASE.md)。
- README 里 npm ≥ 12 的说明改用官方 `allow-scripts` 机制，并明确警告不要再使用即将移除的 `--dangerously-allow-all-scripts`。
- 验证脚本（Windows 侧）此前有四处缺陷已一并修好：窗口计数改为按**句柄**而非类名（避免基线已有同类名窗口时假通过）、`trigger`/`check` 输出不再混入 PowerShell 远程字段、删目录前反复确认端口已空、setup 不再无条件传放行参数。

## 已知限制

- **A2 的根因仍在宿主侧**（交接项 L1）：bundle 就地替换导致运行中实例取到 404，这一条只能由 DSH 宿主解决（给应用根挂 error boundary，或安装期间冻结前端资源替换）。本插件侧的守卫是**兜底**，它不阻止崩溃，只保证不出现永久白屏。
- **systemd 单元与当前实例不一致**时仍会空等约 2 分钟（见上）。
- `--allow-scripts` 的白名单是**安装前**确定的，因此目标版本若引入了全新的原生依赖，首次更新需要靠自愈重试兜一次；插件会持续把新发现的依赖并进静态表与 `.npmrc`。
- **发布后 24 小时内，pnpm 默认安装会回退到旧版**（`minimumReleaseAge` 门禁，静默不报错）。自更新显式带了版本号，不受影响；手工安装请写全 `@yannzhou/dsh-about@1.8.0`。
- 本插件仍然**故意不声明任何 `@deepseek-ai/*` peer 依赖**：它是管更新的插件，必须在任何 dsh 版本下都能加载。
